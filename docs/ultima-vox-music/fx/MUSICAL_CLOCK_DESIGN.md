# Musical clock implementation decision (development, not full-stack proof)

The existing `fx.event.duration` host ID/range remains seconds, 0.05–32; do not overload it. The versioned Program structural duration selects seconds or 1/2/4/8/16 bars. Existing state migrates to seconds. No new host ID is authorized by this decision. The following notes describe the original onset-relative design. See the current policy below.

For bar events the callback integrates quarter-note beats from valid per-block host tempo, preserving phase when tempo changes. An event's bar count and 4/4 meter are snapshotted; host tempo is read at block boundaries until per-sample tempo information is actually available. Event sample N renders while its accumulated beat position is below its target; no RAM scales with duration. Low BPM increases event lifetime, not storage; the fixed eight active voices and bounded retirements still apply. Invalid tempo must not advance the standalone clock; integration must explicitly decide pause versus last valid snapshot, and signal unsupported/missing meter rather than misrepresent host sync. Stop/seek ends held events with bounded fade and retrigger is explicit; existing effects tails remain in their shared processing path. Loop/seek detection and exact DAW policies need integration tests.

Use compensated beat accumulation to limit floating-point drift over millions of samples; the last boundary is measured in samples, not assumed from nominal seconds. The helper accepts its existing wider meter range for testing, but production support must not be claimed until 4/4 host integration and unsupported-signature behavior are implemented. Source changes are snapshotted per event and sample leases remain valid through fades. CC64, note-repeat pairing, unsupported tempo handling and structural-mode persistence remain open integration decisions; no Gate behavior is claimed by this clock change.

## Initial integrated bar one-shot slice

For this development slice, a structural field `bars` is zero for legacy seconds, otherwise exactly 1/2/4/8/16. Existing v1 Programs migrate to zero; v2 appends the field after the original layers. This is a bar-duration **one-shot**, not yet target-aligned Transition or Gate/Continuous. A note starts its local beat clock immediately, not at the next bar. The host must report playing, finite PPQ, 1–1000 BPM and explicit 4/4: otherwise new bar notes are rejected and active bar voices enter a 5 ms release using the last valid tempo, while seconds voices remain unaffected. Unknown meter is not guessed. Stop/seek retains the existing all-voice fade policy. Host tempo changes apply from the next block. That initial slice explicitly rejected bar WAV export. This protects state and avoids pretending unsupported sync is working. Full lifecycle, tonal selection, host feedback and offline capture remain open.

## Current timing/export policy — 2026-11-19

- Bar **Transition** targets the Nth subsequent bar line counted from the bar containing the MIDI trigger. A trigger exactly on a line gets all N bars; a mid-bar trigger shortens the first bar. The host's last-bar PPQ is the grid origin when present; otherwise the grid is zero-based. The absolute target is captured at trigger time. The dry event ends on the first sample at or after the target (within floating-point rounding); shared post-FX can continue. The seconds mode and non-Transition bar durations retain their trigger-relative timelines.
- Only playing, explicit 4/4 hosts with finite PPQ/tempo are accepted for musical triggering. The Transition grid accepts absolute PPQ/origin up to 1,000,000 and 1–1000 BPM. The processor interpolates positions inside a block using that block's starting PPQ and tempo. Intra-block tempo changes not reported by the playhead cannot be observed. Sample-position stop/seek/loop discontinuities fade all voices; PPQ jumps of at least 0.125 quarter notes also fade aligned transitions even when sample time is continuous. Smaller PPQ-only discontinuities can be missed. Loss of the bar grid fades the active aligned voices rather than relocating them.
- FIFO pairing uses two fixed counters per channel/key (32 KiB total). A stolen, replaced, rejected or finite NoteOn still consumes its own NoteOff. CC120/123 and transport/UI panic clear the relevant ownership and fade voices over 5 ms; FX tails continue. MIDI 1.0 cannot identify out-of-order releases of identical channel/key presses. Sustain pedal CC64 is not implemented. Preview and host pattern events do not consume MIDI release slots; Gate/Continuous/Loop preview one finite timeline pass.
- WAV captures a single trigger audition (C4, stereo 48 kHz PCM24 in the editor), not a sequence or the host tempo map. For bars, it starts at PPQ zero and uses the captured BPM (120 when unavailable). Audio payload is capped at 128 MiB before allocation. Serial feedback-delay/reverb tails are included; oversized, cancelled or invalid renders must not replace an existing file. MIDI export still represents trigger notes.
- No host ID, state section format, or plugin identity changes in this checkpoint. Existing FPRG v4 combinations `Transition` + `bars != 0` are intentionally interpreted as host-aligned; the previous development checkpoint interpreted them as onset-relative. Old v1–v3 states still decode to One Shot. DAW project restore and the host-specific playback behavior remain qualification items.
