# VOX FX — prepared WAV and MIDI drag

Development response to [TL review 7031193956](https://github.com/ultima-vox/vox-electronic-engine/pull/156#issuecomment-7031193956). Base integrated into Draft #156: `92dec20afa461f99bf0f5ccce3fe1081be47bf78`. **HOLD / NO MERGE. No Windows opt-in.**

## Workflow

- **MIDI:** choose **Prepare MIDI drag** to capture the current trigger Pattern at the latest observed fixed tempo (120 BPM fallback). When **Drag MIDI snapshot** appears, drag that handle into the host. The temp file is the same Type 0 SMF emitted by Save; it is trigger MIDI, not audio or a recorded host tempo map.
- **WAV:** open **WAV**, set format/rate/note/velocity, and choose **Prepare drag** rather than **Choose file…**. Drag **Drag WAV snapshot** when ready. The same bounded WAV worker renders the captured Program, including its selected sample generation and effects tail policy.
- Keep the existing **MIDI** and **WAV → Choose file…** paths for durable or keyboard-only file export. Preparation does not open a chooser, and moving the drag handle does not start an encode or render. A normal click or a motion under the gesture threshold does not start transfer. One pointer gesture makes at most one call to the native adapter. At this original checkpoint one started drag consumed the prepared handle. The [drag replay follow-up](DRAG_REPLAY_20261119.md) now makes the same file reusable after completion.

## Data and lifetime

One processor-owned slot serves Save and Prepare. Preparation runs off the callback, writes a completed file into an exclusively created subdirectory of OS temp, and hands the ready file lease to the processor. A render or encode receives a value snapshot. The editor and audio callback do not write the file or create its directory. Pending or staged work is not persisted, state schema and all 19 host IDs are unchanged. A prepared file survives closing/recreating the editor without being recomputed. Re-preparation retires an unused file on the worker; processor teardown also retires an unused file. Teardown still cannot promise bounded time if an OS file call blocks. Pinned JUCE also waits for an active Windows OLE drag job at shutdown, so the user may need to cancel an in-flight native drag before unloading.

The drag grip supplies one real `.mid` or `.wav` path to `juce::DragAndDropContainer::performExternalDragDropOfFiles` in `mouseDrag`, with moves **not** allowed. A native start is not evidence of a successful drop or copy. Completion only ends the operation in FX; it does not need a live editor or processor. A file exposed to the native target is deliberately **not** deleted by FX on completion or plugin unload: the target may resolve the path late, and JUCE only reports that the operation ended. This also retains files following a native start that is later canceled. Retained scratch files occupy temp space until the OS or user cleans it; there is no automatic eviction that could invalidate a host reference. Enable **copy into project** in the DAW or use Save to a durable destination; do not keep projects referencing temporary paths.

## What must still be qualified

- Native Windows OLE and actual Cubase/REAPER drop, including copy-vs-reference import, editable SMF, WAV tail, canceled drops, repeated preparation, keyboard Save fallback, and close/unload around an active native operation. Native offscreen fixtures inject the adapter, so they prove call/admission and payload behavior, not OS or DAW behavior.
- Windows Save/dialog and commit scenarios remain in the [candidate gate](CANDIDATE_GATE_20261119.md). **Existing-path policy (development only):** a file observed as already present is eligible for the overwrite selected by the save dialog; FX does not compare its file identity at commit. Replacing a concurrently altered existing file is not prevented, unlike late creation on a previously empty path. Keep this visible in controlled Windows qualification and require explicit acceptance of the existing-path policy before release. No tests should target a real user project.
- No Windows workflow, release merge, fresh-bounce parity claim or listening acceptance follows from this change. The 176-candidate private listening scope is unchanged (zero approved). No new cue ZIP or upload.
